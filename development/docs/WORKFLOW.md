# 协作流程

依据：用户在 2026-10-22 要求保持参与，避免完全交给 Agent 后方向逐步走偏。

1. **修改前说清目标。** 说明这批要改哪些板块、要解决什么问题、怎样验证。较大工作先拆成有独立目的的小批次；不把多个新方向塞进一次交付。
2. **实现中及时告知结构决定。** 新增模块、改变模块职责、调整公共接口时先给简短说明；用户可以在工作中纠正。授权范围内的常规修改继续进行，不反复索要确认。
3. **每批修改后保存解释图。** 图中标明新增/修改/未接入模块，配上原因、影响、接口变化、验证和未验证项，保存到 `development/docs/changes/`；每轮保留对应文件树。2026-10-25用户更新：聊天汇报以建议、关键依据和待决定事项为主，不逐轮展开全部图表、文件和检查记录；需要时提供链接或针对性说明。
4. **以实际代码交接。** 架构发生变化时更新完整文件树、逐文件职责、总流程图、模块总表，不能只给抽象概念图。
5. **真实记录结论。** 测试替身、真实模型、独立文件检查、完整任务验收分别说明；未知用量用 null，失败和未验收不写成通过。
6. **收敛当前批次。** 本批完成后向用户交付可审阅结果；新的功能方向在后续交流中安排，不能自动滚动扩展。

完整交付资料保留本轮结果、修改解释图、模块变化、验证和限制。聊天优先说明建议、重要影响与需要决定的事项；用户要求或结构方向发生变化时再展开。按需检查和有界补救的新授权及待确认方案见[通用可靠性计划](RELIABILITY_PLAN.md)，不能把计划写成已实现能力。

开发与验收资料统一收纳在 `development/`，包括测试代码、脚本、实际运行现场、用量、失败、修改解释图和文件树。Agent 本体位于 `src/clearact_lite/`，不依赖 development/ 的任何文件。

旧记录搬迁后保持原始字节；其中的历史绝对路径可能仍指向旧位置，使用搬迁清单定位当前文件，不改写历史证据。
